# Specification review — open questions and working defaults

Raised during the initial specification review (2026-11-14). Each item states the
working default being used until the product owner decides otherwise.

| # | Topic | Concern | Working default | Status |
|---|---|---|---|---|
| 1 | Stage prompts | Part XI's six stages were not in the master document. | Prompts are supplied one at a time and stored in `prompts/`. | Resolved |
| 2 | Trend data | SteamDB and SteamCharts have no authorised API. | Self-collected player-count history via `ISteamUserStats/GetNumberOfCurrentPlayers` for a bounded set of games; SteamDB/SteamCharts adapters disabled. Trending is empty until ~42 days of history exist. | Open |
| 3 | Recent playtime | Steam reports `playtime_2weeks`, not 30 days. `H_recent` needs 30 days. | Use 2-week value until our own snapshots cover 30 days; mark provenance. | Open |
| 4 | Steam tags | Community tags are not in the documented `appdetails` response. | `IStoreBrowseService/GetItems` returns tags with vote weights; verified live (ADR-0013). | Resolved (Stage 2) |
| 5 | Provider licensing | IGDB commercial terms, RAWG attribution/quotas, OpenCritic paid, HowLongToBeat no API. | Steam only; IGDB needs written confirmation from partner@igdb.com. See docs/PROVIDERS.md. | Open (legal) |
| 6 | OpenID library | No maintained Python OpenID 2.0 library exists. | In-house verifier with `check_authentication`, single-use state and nonce replay protection (ADR-0008). | Resolved (Stage 2) |
| 7 | LightFM | Effectively unmaintained; build problems on Python ≥ 3.12. | Use `implicit` (ALS) plus own content features; LightFM optional evaluation only. | Superseded by #24 |
| 8 | Cold start | Explicit labels will be sparse; training gates will rarely pass early. | Content baseline is the launch engine. | Noted |
| 9 | Sparse metadata | Scoring only known features lets one-tag games score 100. | Coverage-aware shrinkage towards neutral; redistribute weights of fully unknown categories. | Open (Stage: recommendation) |
| 10 | Exclusions vs unknown | A game with unknown metadata cannot be proven free of an excluded feature. | Passes the filter; card states metadata is incomplete. | Default accepted |
| 11 | Score labelling | Pre-model `satisfaction_score` is really a content match. | Label as "Match" in UI/API until a calibrated model exists. | Noted |
| 12 | Opt-out and CF | Opted-out users still deserve CF recommendations. | Fold-in at inference with fixed item factors, no training contribution. | Resolved (Stage 4) |
| 13 | Undefined terms | `previous_comparable_growth`; parent/child counting rule; "owned games in Trending" setting. | `growth_7` one week earlier; most-specific feature per path; a user setting. | Open |
| 14 | Production server | Traefik network, domain, monitoring/logging stack unknown (dev machine ≠ server). | Traefik labels live in the single production `docker-compose.yml` (ADR-0021), parametrised via `.env` (`TRAEFIK_NETWORK`, `TRAEFIK_CERT_RESOLVER`, `TRAEFIK_ENTRYPOINT`, `PUBLIC_HOSTNAME`, `FORWARDED_ALLOW_IPS`). Verified behind a local test Traefik; the real server, domain, ACME certificate and monitoring stack are still to be verified by the owner (tutorial.md, sections C and I). | Open (owner) |
| 15 | Steam data terms | Steam Web API terms: fetch user data only at the user's request; the privacy policy must name what we store and where. | Daily re-sync only for users active in the last 30 days, with an opt-out toggle in Settings (Stage 4). Needs legal review. | Open (legal) |
| 16 | Hidden playtime | Steam's "Always keep my total playtime private" option has no explicit API signal. | Heuristic: ≥5 games all with 0 playtime → `playtime_appears_hidden`, shown in onboarding. | Noted |
| 17 | Stale queued imports | If Redis loses a message, a run can stay `queued` and block new imports. | Add a reaper in a later stage. | Open |
| 18 | **Sign-in only (product decision, 2026-11-14)** | Owner chose no Steam Web API key. Without a key there's no authorised way to read libraries or playtime. | **Reversed 2026-11-15 (ADR-0015):** the owner wants automatic import; an operator key is configured and a live import succeeded. Manual mode remains only as a no-key fallback. | Decided |
| 19 | Store query sort order | `IStoreQueryService/Query` `sort=12` (popularity) is undocumented. | Verified live; the parser is defensive; discovery degrades to charts if it changes. | Open (monitor) |
| 20 | Catalogue prevalence bias | Behavioural lift compares against the shared catalogue, which is mostly early users' libraries plus discovered games. | Accepted for the baseline; revisit with more users or Steam-wide tag counts (docs/RECOMMENDATIONS.md §8). | Open |
| 21 | Score calibration | Matches cluster between 50 and 65 and are not probabilities. | Labelled "Match"; calibrate against post-play feedback in the ML stage (spec §18, §25). | Open |
| 22 | Trending availability | Trend scores need 42 days of self-collected player counts (first sample 2026-11-15). | Unavailable state plus a labelled "Popular right now" list until about 2026-12-27. | Accepted |
| 23 | Price region | Prices come from one storefront country (`STEAM_STORE_COUNTRY`, default US). | Per-user region later (would need the user's country, a privacy decision). | Open |
| 24 | **LightFM (product decision, 2026-11-15)** | Prompt 4 asks to implement and benchmark LightFM; it does not build on Python 3.12 (release or pinned source). | Owner chose to **skip it for now**. ALS and BPR from `implicit`, with hybrid feature pseudo-users, are benchmarked instead. Revisit with the `lightfm-next` fork or a patched source build if wanted (ADR-0009 amendment). | Decided (deferred) |
| 25 | Training consent | Global training is opt-out (on by default). Some jurisdictions may require opt-in consent for using behaviour in training. | Opt-out with a clear Settings toggle and pseudonymised training; needs legal review before public launch (docs/PRIVACY.md). | Open (legal) |
| 26 | Event retention | `behaviour_events` is kept until account deletion and grows with use. | **Stage 6:** daily `prune_data` deletes events after 730 days, recommendation runs after 90 days (never-shown runs after 24 h) and monitoring reports after 400 days, all configurable (DATABASE.md § Retention). Partitioning only if volume requires it. | Resolved (Stage 6) |
| 27 | Satisfaction question thresholds | When a game has been played "enough" to ask about it. | Two hours of play after the first recommendation exposure; at most one new question a week; a two-week snooze; asked at most twice (docs/BEHAVIOUR.md §4). Tune with real response rates. | Open |
| 28 | Collaborative deployment gates | The minimum data and lift needed before a collaborative model affects recommendations. | 25 players, 500 positive pairs, 10 test players, NDCG@5 ≥ 1.05 × popularity (docs/COLLABORATIVE.md §3). Revisit once real data exists. | Open |
| 29 | Satisfaction gates | Minimum labels and quality before predicted enjoyment is shown. | 200 labels, 40 test rows (10 per class), AUC ≥ content + 0.01, log loss ≤ content, ECE ≤ 0.08 (docs/SATISFACTION.md §3). Revisit once real ratings exist. | Open |
| 30 | Reaction label weights | Favourite, dislike and not my type are partial satisfaction labels (0.5 / 0.5 / 0.3). | Documented starting values; evaluate against post-play ratings when both exist for the same games. | Open |
| 31 | Admin access | Prompt 5 asks for manual training by administrators; spec §35 forbids exposed admin endpoints. | CLI in the worker container (`python -m app.cli train`, `rollback`, `models`, `report`, `monitor`). A role-based admin UI would need its own decision. | Decided (CLI) |
| 32 | Monitoring alerts | Alerts are stored in `model_monitoring_reports` but not sent anywhere. | Read via `app.cli monitor` or the database; wire to the operator's alerting once spec §36 observability exists. | Open |
| 33 | Capacity | The 100-user test ran on one host with the production limits (API 2 CPUs). Under aggressive pacing the API CPU is the limit (p95 0.8 s, 0 errors); at realistic pacing p95 is 0.26 s. | Raise API CPUs and `WEB_CONCURRENCY` together on the real server, within the database role's 60 connections (docs/PERFORMANCE.md). Re-test on the server behind Traefik. | Open |
| 34 | Completion times (IGDB) | IGDB is the only authorised completion-time source found; its terms for this use must be confirmed and it needs Twitch app credentials. | Adapter, attribution and tests are in place; `IGDB_ENABLED=false` until the owner confirms the terms and adds credentials. Cards show nothing rather than guesses. | Open (owner) |
| 35 | Player-count source | Neither SteamCharts nor SteamDB offers a public API or terms permitting reuse; SteamDB's terms forbid scraping, and scraping is not assumed permitted (docs/PROVIDERS.md). | Counts are sampled from Steam's own `GetNumberOfCurrentPlayers`; trend history builds up from the first sample (see #22). | Decided |
| 36 | Visual browser check | The Chrome extension was not connected during Stage 6. | Headless Chromium via Playwright (`scripts/browser-check.py`) at desktop and phone sizes; a manual pass in a real browser is still worthwhile before launch. | Noted |
| 37 | Stale queued imports (#17) | Still no reaper for runs left `queued` if Redis loses a message. | Low risk with Redis persistence (AOF); add a reaper if it is ever seen. | Open |
| 38 | **Scoring mode switch (owner request, 2026-11-15)** | The owner wants one deployment-wide variable to choose machine-learning or classic, non-ML scoring. | `AI_GRADE=TRUE\|FALSE` (default TRUE, strict values), selected in one engine module; runs store `scoring_mode` and `config_version`; lists from the other mode are never shown and are rebuilt on demand; scheduled training and monitoring are skipped in classic mode; events and models are kept (ADR-0020, docs/SCORING_MODES.md). | Decided |
| 39 | **Single production Compose file (owner request, 2026-11-15)** | Production needed three Compose files combined by hand. | Superseded in part by #41. One `docker-compose.yml` for production; `compose.dev.yaml` is an optional workstation overlay; one `.env.example`; tutorial.md is the install guide, DEPLOYMENT.md the design (ADR-0021). | Decided |
| 40 | "Suggest another one" | The AI_GRADE request lists this feature, which does not exist in the product. | Not built (out of scope). Any future version must read lists through `GET /api/me/recommendations/{category}` or `generate_all` so it follows AI_GRADE (docs/SCORING_MODES.md). | Open (owner) |
| 41 | **Two-command deployment (owner request, 2026-11-16)** | Deployment still needed helper scripts, `docker compose build`, a version variable and a `COMPOSE_FILE` overlay. | `./build.sh` (images tagged `1.0`) then `docker compose up -d`; `docker-compose.yml` has no `build:`; PostgreSQL scripts packaged in `wdywtp-postgres:1.0`; live volume `wdywtp_postgres-data` reused; workstation overlay moved to `docker/dev/compose.dev.yaml` (ADR-0022). | Decided |
